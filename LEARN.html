MeetBuddy

A complete walkthrough of the codebase — written to help you learn the full system from scratch.

What This App Does

MeetBuddy automatically records your Google Meet calls, transcribes the audio, extracts insights (summary, action items, decisions), and lets you search across all your past meetings using plain English questions.

Three moving parts:

  • Chrome Extension — captures audio during a live meeting
  • FastAPI Backend — processes audio and stores everything
  • Next.js Web App — shows results and lets you query them

System Architecture Overview

Chrome Extension (background.ts) │ detects Google Meet tab │ captures tab audio via MediaRecorder │ streams chunks via WebSocket every 5 seconds ▼ FastAPI API (main.py) ←→ PostgreSQL (with pgvector) │ receives audio chunks ↑ │ stores audio in MinIO models │ triggers Celery pipeline │ ▼ │ Celery Worker (tasks/pipeline.py) ────────┘ │ transcribes audio (Whisper) │ embeds transcript chunks (sentence-transformers) │ extracts insights (LLM) │ marks meeting "done" ▼ MinIO (S3-compatible object storage) stores: raw audio files, transcript JSON files Next.js Web App reads from FastAPI to show meetings, transcripts, insights query page: sends a question → API does vector search → LLM answers

Backend Deep Dive apps/api/

Configuration — config.py

Uses pydantic-settings to read environment variables. Every config value is one attribute on the Settings class. Values come from a .env file at project root.

Key settings:

  • database_url — PostgreSQL connection string (uses asyncpg driver for async support)
  • redis_url — Redis for Celery
  • storage_* — MinIO credentials and endpoint
  • jwt_secret — used to sign/verify JWT tokens
  • llm_provider — switches between ollama (local), openai, or anthropic
  • whisper_model — size of the Whisper speech-to-text model (base, small, medium…)

Database Setup — database.py

engine = create_async_engine(settings.database_url, echo=False)
AsyncSessionFactory = async_sessionmaker(engine, expire_on_commit=False)

This creates an async SQLAlchemy engine. Async means database calls don't block the server while waiting for a result — FastAPI can handle other requests at the same time.

get_db() is a FastAPI dependency that yields a session, commits on success, and rolls back on any exception. Routes receive this session via Depends(get_db).

Data Models — models/

User

Stores email, name, avatar URL, and a bcrypt-hashed password. ID is a UUID.

Meeting

The core entity. Tracks:

  • Which user it belongs to (user_id foreign key)
  • Which platform (google_meet, etc.)
  • Status lifecycle: "recording" → "processing" → "done"
  • Where the audio file lives in MinIO (audio_url = a storage key like audio/<uuid>/recording.webm)
  • Where the transcript JSON lives (transcript_url = MinIO key)
  • Related data via SQLAlchemy relationships: speakers, chunks, insights

Speaker

Represents one speaker identified in the recording. Has a label (like "SPEAKER_0") and an optional name. Speaker diarization is a Phase 2 feature — not fully wired yet.

Chunk

A segment of the transcript. Stores the text, start/end timestamps, and — critically — a 768-dimension embedding vector. This is what enables semantic search. The embedding column uses pgvector.sqlalchemy.Vector(768).

MeetingInsights

One row per meeting (1:1 relationship). Stores summary, action_items, decisions, topics as JSONB arrays, plus the raw LLM output.

MemoryEntity

Stores named entities (people, companies, projects) extracted from meetings for cross-meeting memory. Not yet connected to the main pipeline.

Database Migration — alembic/versions/0001_initial_schema.py

Alembic manages schema changes. The first migration:

  1. Creates the vector PostgreSQL extension (required by pgvector)
  2. Creates all tables in dependency order (users → meetings → speakers → chunks → meeting_insights → memory_entities)
  3. Creates an IVFFlat index on chunks.embedding — this makes vector similarity searches fast at scale

The downgrade() function drops everything in reverse order. Always write downgrade — it lets you undo a migration.

Authentication

JWT-based auth with access + refresh tokens.

EndpointWhat it does
POST /auth/registerCreates user, hashes password with bcrypt, returns both tokens
POST /auth/loginLooks up user, verifies bcrypt hash, returns tokens
POST /auth/refreshVerifies refresh token, issues a new pair
DELETE /auth/logoutStateless — client drops its token. A blocklist would go here.
GET /auth/meReturns current user's profile

JWT structure

Every token payload has three fields:

  • sub — the user's UUID (the "subject")
  • type — either "access" or "refresh" (prevents using a refresh token as an access token)
  • exp — expiry timestamp

Access tokens expire in 60 minutes. Refresh tokens expire in 30 days. passlib with bcrypt handles password hashing. python-jose handles JWT encoding/decoding.

How auth guards work

Any route that needs authentication has this dependency:

async def get_one(
    id: uuid.UUID,
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
):

get_current_user reads the Authorization: Bearer <token> header, decodes the JWT, looks up the user in the database, and returns the User object. If anything fails, it raises a 401. All protected routes then automatically receive the User object — FastAPI calls these "dependency injection" and it's one of the framework's best features.

Audio Upload — routes/upload.py

Two endpoints for when the extension uploads a completed file (alternative to streaming):

  • POST /upload/audio — accepts a file upload, verifies ownership, uploads bytes to MinIO at key audio/<meeting_id>/<filename>, saves the key to meeting.audio_url
  • POST /upload/complete — signals upload is done, sets status to "processing", kicks off the Celery pipeline

WebSocket Streaming — routes/websocket.py

WS /api/v1/ws/{meeting_id} — used by the extension during a live meeting.

The server keeps an in-memory dict AUDIO_CHUNK_STORE mapping meeting_id → list[bytes].

Protocol

1
Client sends {"type": "chunk", "audio_b64": "...", "seq": 0} every 5 seconds
2
Server decodes the base64 audio and appends to the in-memory list
3
Client sends {"type": "stop"} when the meeting ends
4
Server concatenates all chunks, uploads to MinIO, triggers the pipeline
Known limitation AUDIO_CHUNK_STORE lives in process memory. In a multi-process deployment, chunks are lost if requests hit different workers. A real fix uses Redis or shared storage for the chunks.

The Processing Pipeline — tasks/pipeline.py

Celery is a task queue — it lets you run code asynchronously in a separate worker process. This is essential because transcription and LLM calls can take minutes; you don't want them blocking an HTTP request.

Setup — tasks/celery_app.py

celery_app = Celery(
    "meetbuddy",
    broker=settings.redis_url,   # Redis receives the task message
    backend=settings.redis_url,  # Redis stores the result
    include=["tasks.pipeline"],
)

The Pipeline Chain

def process_meeting(meeting_id: str) -> None:
    pipeline = chain(
        transcribe_audio.si(meeting_id),       # Step 1
        store_and_embed_chunks.si(meeting_id), # Step 2
        extract_insights_task.si(meeting_id),  # Step 3
        mark_complete.si(meeting_id),          # Step 4
    )
    pipeline.delay()

chain() runs tasks in sequence — step 2 only starts after step 1 completes. .si() means "ignore the return value of the previous task". .delay() sends the chain to Redis so the Celery worker picks it up.

Async/Sync Bridge

Celery tasks are synchronous but the database layer is async. The bridge:

def _run(coro):
    return asyncio.get_event_loop().run_until_complete(coro)

# Inside every Celery task:
async def _run_async():
    async with AsyncSessionFactory() as db:
        ...  # actual async work

_run(_run_async())

Four Steps in Detail

Step 1 — transcribe_audio

Loads the meeting, sets status to "processing", downloads audio from MinIO, writes to a temp file, runs faster-whisper (beam_size=5), uploads transcript JSON back to MinIO, saves the key.

Step 2 — store_and_embed_chunks

Downloads transcript JSON, extracts all segment texts, runs them through the embedding model to produce 768-dim vectors, creates a Chunk row for each segment with its vector. This is what enables semantic search.

Step 3 — extract_insights_task

Downloads transcript JSON, concatenates all text, calls the LLM with the extraction prompt, saves a MeetingInsights row.

Step 4 — mark_complete

Sets meeting.status = "done".

Retry logic All tasks have max_retries=3 and bind=True (so they can call self.retry()). If a step fails, it retries after 30 seconds. This makes the pipeline resilient to transient failures like network blips or model load errors.

Transcription Service — services/transcription.py

Lazy loading: Both the Whisper model and the embedding model are loaded once on first use (via module-level None globals). This avoids loading multi-GB models at import time.

transcribe_audio_file(audio_key)

  1. Downloads audio bytes from MinIO
  2. Writes to a temp .webm file (Whisper needs a file path, not bytes)
  3. Runs model.transcribe(path, beam_size=5) — higher beam size = slightly better accuracy, slower
  4. Returns segments as dicts: [{"text": "...", "start": 0.0, "end": 2.3}, ...]
  5. Deletes the temp file

embed_texts(texts)

  1. Runs model.encode(texts, normalize_embeddings=True, batch_size=32)
  2. normalize_embeddings=True means vectors have length 1, so cosine similarity equals the dot product (faster)
  3. Returns a list of 768-dim float arrays — one per text segment
Why asyncio.to_thread()? All CPU-intensive work (Whisper inference, embedding) runs via asyncio.to_thread() — this moves blocking work off the async event loop into a thread pool, so FastAPI can handle other requests while the model is running.

extract_insights(transcript)

Loads extract_insights.txt prompt, substitutes {transcript}, calls the LLM, parses the response as JSON. Has a regex fallback to find {…} if the LLM adds surrounding text.

Loads query_meetings.txt prompt, substitutes {context} (retrieved chunks) and {question}, returns the LLM's text answer.

LLM Prompts — prompts/

extract_insights.txt

Tells the LLM to return ONLY valid JSON with no explanation. The schema has summary, action_items, decisions, topics. Enforcing JSON output is necessary because you need to save structured data to the database, not free text.

query_meetings.txt

Tells the LLM to answer based ONLY on provided excerpts (RAG pattern). If the answer isn't in the excerpts, say so. This prevents the LLM from hallucinating things that were never said in your meetings.

extract_entities.txt

Extracts people, companies, and projects from a transcript into JSON. Intended for the memory system (MemoryEntity table) — not yet fully wired into the main pipeline.

Semantic Search — services/query.py

This is the "ask a question across all your meetings" feature. It implements the RAG (Retrieval-Augmented Generation) pattern.

async def semantic_search(req, user_id, db):
    # 1. Embed the user's question into a vector
    query_embedding = await embed_text(req.q)

    # 2. Find the 8 most similar chunks using pgvector's <=> operator (cosine distance)
    base_query = (
        select(Chunk.id, Chunk.meeting_id, Chunk.text, Chunk.start_time)
        .join(Meeting, Chunk.meeting_id == Meeting.id)
        .where(Meeting.user_id == user_id)
        .order_by(text(f"embedding <=> '{embedding_str}'::vector"))
        .limit(SIMILARITY_LIMIT)  # 8 chunks
    )

    # 3. Feed those chunks as context to the LLM
    answer = await answer_query(req.q, "\n".join(context_parts))
1
Convert question to vector. The same embedding model used during indexing is applied to the user's question.
2
Vector similarity search. <=> is pgvector's cosine distance operator. The IVFFlat index makes this fast. "pricing discussion" matches "cost debate" because their vectors are close — keyword search would miss this.
3
LLM answers grounded in your actual meetings. The retrieved excerpts become context; the LLM generates an answer citing them.

Object Storage — utils/storage.py

Uses boto3 (the AWS SDK) pointed at MinIO — MinIO implements the S3 API, so the same code works with real AWS S3 in production. Three operations:

  • upload_file(key, data, content_type) — put_object to the bucket
  • download_file(key) — get_object, reads the full body
  • get_presigned_url(key, expires_in=3600) — generates a signed URL valid for 1 hour, used to let the web app serve audio without proxying through the API

The client is lazily initialized with a module-level singleton (_client = None).

Recording flow

1
handleMeetTabOpened — gets auth token from chrome.storage.local, calls API to create a meeting record, calls startRecording
2
startRecording — uses chrome.tabCapture.getMediaStreamId to get the tab's audio stream, creates a MediaRecorder with audio/webm;codecs=opus
3
Opens a WebSocket connection to the backend
4

5

content.ts — The Content Script

Injected into every meet.google.com page. Watches the DOM for participant tile elements using a MutationObserver. When participants change, it waits 2 seconds (debounce), extracts names from the DOM, and sends them to the background service worker via chrome.runtime.sendMessage. Used for speaker diarization (Phase 2 — not yet wired).

popup/index.tsx — Settings Popup

A small React form that saves two values to chrome.storage.local:

  • apiUrl — which backend to talk to
  • accessToken — the JWT to authenticate with

You paste your token from the web app. This is how the extension knows who you are.

sidepanel/index.tsx — Side Panel UI

Shows recording status during a meeting. Listens to chrome.storage.onChanged — whenever recordingState changes in storage (set by the background when recording starts/stops), the UI updates automatically. Has a "Stop recording" button that sends STOP_RECORDING to the background.

End-to-End Flow

What happens from you joining a Google Meet to being able to ask "what did we decide?"

You open meet.google.com

  • Extension detects the URL
  • Calls POST /api/v1/meetings to create a meeting record
  • Captures tab audio with MediaRecorder

Every 5 seconds while meeting runs

  • Audio chunks sent as base64 over WebSocket
  • Server buffers them in memory (AUDIO_CHUNK_STORE)

Meeting ends (tab closes or you click Stop)

  • Extension sends {"type": "stop"}
  • Server concatenates all audio bytes
  • Uploads to MinIO: audio/<uuid>/recording.webm
  • Sets meeting.status = "processing"
  • Fires process_meeting(meeting_id) into Celery queue

Celery worker — Step 1: Transcription

  • Downloads audio from MinIO
  • Runs faster-whisper (speech-to-text)
  • Uploads transcript JSON back to MinIO

Celery worker — Step 2: Embedding

  • Downloads transcript JSON
  • Runs each segment through nomic-embed-text
  • Stores Chunk rows with 768-dim vectors in PostgreSQL

Celery worker — Step 3: Insight Extraction

  • Downloads transcript, concatenates all text
  • Sends to LLM with extract_insights prompt
  • Saves MeetingInsights row (summary, action items, decisions, topics)

Celery worker — Step 4: Done

  • Sets meeting.status = "done"

You open the web app

  • Sees the meeting listed as "done"
  • Clicks it → sees summary, action items, decisions, transcript

You type "what did we decide about pricing?"

  • Web app POSTs {"q": "what did we decide about pricing?"}
  • API embeds your question (same 768-dim model)
  • PostgreSQL cosine similarity search finds top 8 chunks
  • Those chunks become context for the LLM
  • LLM answers grounded in your actual meeting content
  • You see the answer with links back to the source meetings

Key Patterns to Learn From

Dependency Injection in FastAPI

@router.get("/{id}")
async def get_one(
    id: uuid.UUID,
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
):

FastAPI calls get_db and get_current_user automatically for every request. If get_current_user raises a 401, the route function never even runs. This keeps auth logic out of every route handler.

Async-to-Sync Bridge (Celery Tasks)

@celery_app.task(bind=True, max_retries=3)
def my_task(self, meeting_id: str):
    async def _work():
        async with AsyncSessionFactory() as db:
            ...

    try:
        asyncio.get_event_loop().run_until_complete(_work())
    except Exception as exc:
        raise self.retry(exc=exc, countdown=30)

Singleton Lazy Init (Expensive Models)

_model = None

def get_model():
    global _model
    if _model is None:
        _model = ExpensiveModel()   # loads GB of weights once
    return _model

Pydantic for Validation and Serialization

  • Input schemas (e.g., MeetingCreate) — validate and parse incoming JSON automatically
  • Output schemas (e.g., MeetingResponse) — control exactly which fields are returned
  • from_attributes = True in Config — allows reading directly from SQLAlchemy model instances

RAG — Retrieval-Augmented Generation

The query pipeline is a textbook RAG implementation:

  1. Index time: embed each transcript segment → store vector in DB
  2. Query time: embed the question → vector search → retrieve top-K relevant chunks → feed as LLM context → generate grounded answer

The key insight is that the LLM only "knows" what's in the retrieved context, so answers are grounded in your actual meeting data rather than the model's training data.
